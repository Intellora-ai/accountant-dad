# Communication Rules — Clarification Engine, Internal

> How the seven Clarification sub-engines communicate with one another.
>
> Companion to [`ENGINE_4_CLARIFICATION_ENGINE_RULES.md`](ENGINE_4_CLARIFICATION_ENGINE_RULES.md). **Specification only — no implementation.**
>
> This document governs communication *inside* Engine 4. The boundary into it is governed by [`COMMUNICATION_RULES_ACCOUNTING_ENGINE.md`](COMMUNICATION_RULES_ACCOUNTING_ENGINE.md).

---

# 1. Flow

The flow is intentionally **one-directional**. Feedback occurs only through new artifact versions generated by the responsible upstream engine. Engine 4 never edits previous artifacts.

```text
Accounting Decision  (+ Business Understanding Object, reference only)
        ↓
missing_information      → Missing Information Result
        ↓
uncertainty_detection    → Uncertainty Analysis Result
        ↓
understanding            → Conflict Analysis Result
        ↓
stop_decision            → Clarification Necessity Result
        ↓
answer_understanding     → Clarification Priority Result
        ↓
question_generator       → Clarification Request
        ↓
decision_updater         → Clarification Status Result
```

## Why this order

Each step needs the one before it:

- **What is missing** must be known before uncertainty can be measured — absence is one of uncertainty's sources.
- **Uncertainty** must be measured before contradictions can be weighed — a conflict between two low-confidence readings is not the same finding as one between two reliable ones.
- **Conflicts** must be identified before necessity can be judged — a contradiction is often the thing that makes clarification unavoidable.
- **Necessity** must be settled before priority — nothing unnecessary gets ranked.
- **Priority** must be settled before the request is built — priority is a field of the request.
- **The request** must exist before its lifecycle can be tracked.

## Sub-engine ownership

| Sub-engine | Owns the question |
|---|---|
| `missing_information` | What required information is missing? |
| `uncertainty_detection` | Does uncertainty exist, and how severe? |
| `understanding` | Do the outputs conflict? |
| `stop_decision` | Is clarification required at all? |
| `answer_understanding` | Which clarification matters most? |
| `question_generator` | What exactly is being requested? |
| `decision_updater` | Where is this clarification in its lifecycle? |

Each owns **only** its question. No sub-engine answers another's, even when it can see the answer. Why each historical name owns its current responsibility is stated in [`ENGINE_4_CLARIFICATION_ENGINE_RULES.md` §9](ENGINE_4_CLARIFICATION_ENGINE_RULES.md#name-and-responsibility).

# 2. Communication Rules

---

## Rule 1 — Communicate only through defined artifacts

Each sub-engine publishes exactly one named Result, and that Result is the entirety of what siblings may see.

| Sub-engine | Publishes |
|---|---|
| `missing_information` | Missing Information Result |
| `uncertainty_detection` | Uncertainty Analysis Result |
| `understanding` | Conflict Analysis Result |
| `stop_decision` | Clarification Necessity Result |
| `answer_understanding` | Clarification Priority Result |
| `question_generator` | Clarification Request |
| `decision_updater` | Clarification Status Result |

---

## Rule 2 — Every output carries confidence and evidence references

No Result may omit either, and no Result may raise confidence.

Every finding points back — through the Accounting Decision and the Business Understanding Object — to the evidence that produced it. A finding with no evidence reference cannot appear in a Result. There is no mechanism for producing one, and that is deliberate: it is the structural reason this engine cannot invent uncertainty any more than it can invent facts.

> **Clarification Confidence may never exceed upstream confidence.**

---

## Rule 3 — No sub-engine edits another sub-engine's output

A Result is **read-only** to every sibling, permanently.

A sub-engine that believes a sibling's Result is wrong does not correct it. It records the disagreement in its own Result, and it travels forward with everything else.

This holds for `question_generator` too. Assembly is not permission to edit.

---

## Rule 4 — No hidden communication paths exist

No shared mutable state. No side channels. No implicit coupling through anything other than a published Result.

If a sub-engine needs something a sibling knows, that something must be part of the sibling's Result — named, traceable, challengeable. If it is not in the Result, it is not available, and the correct response is to record that the determination could not be made.

---

## Rule 5 — No circular reasoning is permitted

The flow is one-directional and acyclic. No sub-engine consumes an output derived from its own.

Circularity would be particularly corrosive here: an engine whose purpose is to detect uncertainty could quietly use its own conclusions as evidence that the uncertainty was resolved.

---

## Rule 6 — Conflicts remain visible until resolved

Engine 4 **never** resolves a conflict. Every conflict stays visible until either new information arrives and the responsible upstream engine emits a new artifact version, or the conflict is explicitly accepted by a future validation or human process.

A Clarification Request carrying an unresolved conflict is **correct output**, not a failure.

---

## Rule 7 — The parent assembles but never rewrites history

| Parent **CAN** | Parent **CANNOT** |
|---|---|
| Assemble the final Clarification Request | Rewrite any sub-engine output |
| Organize outputs | Remove uncertainty |
| Create the final structure | Increase confidence |
| | Resolve a conflict |
| | Change a priority |
| | Decide accounting treatment |

**`question_generator` creates the Clarification Request. The Clarification Engine owns it** — along with Clarification Status and Clarification History. `question_generator` does not become an independent owner.

---

# 3. Lifecycle Communication

`decision_updater` is the only component that writes Clarification Status. Every other sub-engine's Result is an input to the request; none of them may set or change its state.

| State | Trigger |
|---|---|
| **Created** | `question_generator` assembles the Request after `stop_decision` returned *clarification required* |
| **Waiting for Information** | Request handed to the external actor |
| **Information Received** | External actor supplies a Clarification Answer — **recorded, never interpreted** |
| **Obsolete** | An upstream engine emits a version newer than Related Artifact Version |
| **Closed** | A new artifact version no longer carries the uncertainty that caused the request |

`Obsolete` may be entered from any state; `Closed` and `Obsolete` are terminal. **Engine 4 owns every transition but no resolution** — resolution is an upstream engine emitting a new artifact version. Full state machine: [`ENGINE_4_CLARIFICATION_ENGINE_RULES.md` §7](ENGINE_4_CLARIFICATION_ENGINE_RULES.md#7-clarification-lifecycle).

---

# 4. What These Rules Protect

Every rule above defends one property: **an uncertainty named in the Clarification Request can be traced to the evidence that produced it, its severity is the severity that evidence supports, and nothing that was found has been quietly unfound.**

Break any one and that property goes:

- Allow a side channel, and an uncertainty appears with no basis — or disappears with none.
- Allow a sub-engine to edit a sibling's Result, and the author of a finding is no longer knowable.
- Allow confidence to be raised, and the number stops meaning anything.
- Allow the parent to adjust what it assembles, and an eighth decision-maker exists that appears in no diagram.
- Allow a conflict to be resolved internally, and the system reports certainty it never had.
- Allow circular reasoning, and the engine can talk itself out of the very doubt it exists to raise.

None of these fail loudly. They all produce a cleaner-looking pipeline than the honest version — which is exactly why they are prohibitions rather than guidance.
